# Deployment Guide ($0 cost)

This app is deployed across three independent free tiers, chosen after checking each provider's *current*
terms directly (official docs/pricing pages, not assumptions):

| Layer | Provider | Why |
|---|---|---|
| Frontend | **Cloudflare Pages** | Free static hosting, unlimited bandwidth, automatic HTTPS, no credit card to sign up. |
| Backend | **Render** (Web Service, free plan) | Runs our existing Node/Express app as-is (no rewrite needed), 750 free instance-hours/month, no credit card required for the free plan. |
| Database | **Neon** (free Postgres) | Permanent free plan (not a trial): 0.5 GB storage, 100 compute-hours/month, no credit card. If a limit is hit it **suspends**, it does not auto-charge. |

**Why not Render's built-in Postgres?** Render's own free Postgres database is deleted 30 days after
creation (confirmed in Render's docs) — unsuitable for anything meant to stay up. Neon's free plan has no
such expiry.

**Why not Railway or Fly.io?** As of this deployment, Railway's free allowance is $1/month of credit after a
one-time $5 trial (not enough to reliably run a persistent service without risking suspension), and Fly.io
has removed its old permanent free allowance for new accounts in favor of a short trial that then requires a
card. Both were rejected specifically because they no longer meet "$0, no card, no surprise charge."

## Architecture

```
Browser
  │  HTTPS
  ▼
Cloudflare Pages (frontend, static React build)
  │  HTTPS fetch, credentials: include
  ▼
Render Web Service (backend, Node/Express)
  │  Prisma / PostgreSQL wire protocol, TLS
  ▼
Neon (managed PostgreSQL)
```

The frontend and backend are on different domains (`*.pages.dev` and `*.onrender.com`), so this is a genuine
cross-site deployment. Two things in the code specifically account for that (see "Code changes made for
deployment" below): CORS is locked to the exact frontend origin, and the refresh-token cookie uses
`SameSite=None; Secure` in production so the browser will still send it across sites over HTTPS.

## Code changes made for deployment

1. **`backend/src/modules/auth/auth.controller.ts`** — the refresh-token cookie's `sameSite` attribute is now
   `"none"` in production (was hardcoded `"lax"`, which browsers block on cross-site requests) and stays
   `"lax"` in development, where the Vite dev proxy makes requests same-site.
2. **`render.yaml`** (new) — a Render Blueprint that deploys `backend/` with the exact build/start commands,
   health check, and environment variable slots this project needs. JWT secrets are generated by Render
   itself (`generateValue: true`) and never appear in this file. `DATABASE_URL` and `CORS_ORIGIN` are declared
   with `sync: false`, meaning Render prompts for them once during setup and stores them as secrets — they
   are never written to git.
3. **`frontend/public/_redirects`** (new) — a single line (`/* /index.html 200`) so that Cloudflare Pages
   serves `index.html` for client-side routes like `/doctors/123` or `/appointments` instead of 404ing on a
   direct load or refresh. Without this, only the `/` route would work.
4. **`.env.example` files** — comments updated to show the production values these variables take (no real
   values added).

No application functionality, business logic, or security behavior was weakened — only genuinely
deployment-required configuration was touched.

## One-time manual setup (requires your own accounts)

Account creation on Render, Neon and Cloudflare needs interactive sign-up (email/GitHub OAuth), which can't be
automated from here. These are the only manual steps; everything else (migrations, environment wiring,
testing) is handled programmatically once you hand back the resulting URLs.

### 1. Neon (database) — create first, so its URL is ready for step 2

1. Go to neon.com → sign up (GitHub OAuth is fastest) → **no credit card required**.
2. Create a project (any name/region).
3. Copy the **connection string** shown (starts with `postgresql://...`, already includes `sslmode=require`).
   Keep it somewhere you can paste it back to me — I'll use it once to run production migrations, then it
   only needs to live in Render's environment variables (never in git).

### 2. Render (backend)

1. Go to render.com → sign up with GitHub → **no credit card required** for the free plan.
2. New → **Blueprint** → select the `Online-Appointment-Booking` repo. Render will detect `render.yaml` at
   the repo root automatically.
3. When prompted, paste in:
   - `DATABASE_URL` → the Neon connection string from step 1
   - `CORS_ORIGIN` → leave a placeholder for now (e.g. `https://placeholder.pages.dev`) — you'll update it
     after step 3 gives you the real Cloudflare Pages URL.
4. Deploy. Note the resulting service URL, e.g. `https://appointment-booking-api.onrender.com`.

### 3. Cloudflare Pages (frontend)

1. Go to dash.cloudflare.com → sign up → **no credit card required**.
2. Workers & Pages → Create → Pages → **Connect to Git** → select the repo.
3. Build settings:
   - Root directory: `frontend`
   - Build command: `npm run build`
   - Build output directory: `dist`
   - Environment variable: `VITE_API_BASE_URL` = `https://<your-render-url>/api` (from step 2)
4. Deploy. Note the resulting URL, e.g. `https://online-appointment-booking.pages.dev`.
5. Go back to Render's dashboard and update `CORS_ORIGIN` to this exact URL, then trigger a redeploy (Render
   redeploys automatically when an env var changes).

### 4. Hand back to continue automated setup

Once you have the Render URL, the Cloudflare Pages URL, and the Neon connection string, share them here (the
connection string only needs to be pasted once, to run migrations — it will not be echoed back or committed).
From there, production migrations, seeding, and full live testing of every flow (register, login, booking,
cancellation, refresh tokens, etc.) will be completed and reported.

## Free-tier limits to be aware of going forward

- **Render**: the backend sleeps after 15 minutes with no traffic; the first request after that takes
  30–60 seconds to wake it up. This is normal free-tier behavior, not a bug. 750 free hours/month is enough
  for one always-available service run continuously across a month.
- **Neon**: 0.5 GB storage and 100 compute-hours/month. Well within range for a demo app; if ever exceeded,
  Neon suspends compute until next month rather than charging anything.
- **Cloudflare Pages**: 500 builds/month — irrelevant unless you push dozens of commits a day.
- None of the three platforms bills automatically on overage; each either suspends or blocks further usage
  until you'd manually choose to upgrade, which this deployment does not do.
